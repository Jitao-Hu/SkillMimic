全局训练架构设计（HRL Dual Pass-and-Catch）
========================================

本文件用于后续让 Agent/工具链实现 HRL Dual Pass-and-Catch 任务时作为“设计说明书”使用。
目标是：在不频繁翻代码的前提下，让实现者一眼看清整体框架、关键模块、输入输出以及代码对应关系。

------------------------------------------------------------
1. 总体目标与范式
------------------------------------------------------------

任务：双人篮球传接球 Pass-and-Catch。
- 机器人 A：主要负责持球、传球。
- 机器人 B：主要负责跑位、接球。

范式：层级强化学习 + CTDE（Centralized Training, Decentralized Execution）。
- 训练阶段：集中式 Critic + 分布式参数共享 Actor + 预训练 LLC。
- 部署阶段：仅 Actor + LLC，无集中式 Critic，两机器人互不直接通信，只通过各自观测和 Role 来区分职责。

预训练 LLC（SkillMimic LLC）已经具备多种人类 HOI 技能：
- 例如：pick（捡球）、pass（传球）、catch（接球）、run/dribble（跑动/运球）、layup（上篮）。
- LLC 接收高层的“技能指示”（skill id / latent code），输出底层关节控制信号（例如 PD 目标或关节力矩）。

在 HRL Dual 里，我们的工作是：
- 设计高层 Actor（HLC）让其为 A/B 决策“选哪个技能、在什么时候用”；
- 设计合适的观测与奖励，让 A/B 学会协同配合完成稳定的传接球。


------------------------------------------------------------
2. 关键组件拆解
------------------------------------------------------------

2.1 Actors（分布式执行器 / HLC）
--------------------------------

本质上是共享参数的高层策略网络，分别在机器人 A 和机器人 B 上运行。

输入（Observation）——局部 + 任务相关视角：
- 自身躯干和关节状态（来自环境基础观测，humanoid_obs）。
- 球相对于自身和对方的空间关系（obj_obs、other_humanoid_obs）。
- 任务相关的高层特征（task_obs），例如：
  - 球相对于接球手手中心的位置；
  - 球速度、预测落点；
  - 对方的速度等。
- 条件/文本嵌入（condition embedding），来自 MotionDataHandler，对应当前技能/数据类。
- Role ID（“传球手 / 接球手”）：在当前代码里通过观测结构 + 控制映射隐式编码，而不是单独的 int，但逻辑上可以理解为：
  - Role 0：传球手（主要产出 pass / run / idle）。
  - Role 1：接球手（主要产出 catch / run / idle）。

输出（Action）：
- 对 HRL Dual 而言，是一个离散的“技能对”索引，由 HLC 输出的动作 a_high。
- 通过 control_mapping 映射为具体的 LLC 技能 ID：
  - 对单人 HRL（hrl_players_discrete）：action -> skill_id。
  - 对双人 HRL Dual（hrl_dual_agent / hrl_dual_players）：action -> (skill_id_A, skill_id_B)。

职责：
- 根据当前局部观测（包含球、对手位置和预测轨迹）和 Role，决定“现在做什么技能”，例如：
  - A：持球 → 找到合适时机 → 选择 pass → 传给 B。
  - B：看到球将飞来 → 跑位 → 选择 catch → 起跳接球。


2.2 LLC（底层控制器 / Motor Skills）
-----------------------------------

LLC 是 SkillMimic 的基础组件，是一个预训练好的低层控制网络，负责把“技能 ID + 当前状态”转成物理上可行、拟人的动作。

输入：
- 高层技能指示：
  - 在实现中通过 64 维 one-hot 向量（control_signal）编码 skill id：
    - skill id 取值来自 motion 类别（BallPlay-M 数据集中 .pt 文件名前三位数字）。
    - 比如：1=pick、3=catch、4=pass、13=run、31=layup 等。
- 环境状态：
  - humanoid_obs + obj_obs（LLC 视角下的躯干、关节、物体状态）。

输出：
- 对应当前技能的底层关节控制：
  - 可是扭矩 torques，也可以是 PD 目标（具体见 SkillMimic 原始实现）。

职责：
- 确保在复杂物理环境中，机器人执行“跑、跳、传球、接球”等动作时不摔倒、不爆炸；
- 平滑执行高层 HLC 发出的技能指令，保持接近人类的运动风格。


2.3 Centralized Critic（集中式 Value 网络，仅训练使用）
------------------------------------------------------

Centralized Critic（全局 Critic）只在训练阶段存在，不会部署到实际执行中。

输入（Global State）：
- 机器人 A 的完整状态（位置、速度、朝向等）；
- 机器人 B 的完整状态；
- 球的状态（位置、速度）、接触信息等；
- 其他必要的环境变量。

输出（Value）：
- 全局状态 s_global 下的标量价值 V(s_global)，代表“当前局面从合作角度看有多好”。

职责：
- 不仅评价单个机器人是否成功，还要评估“协作是否成功”：
  - 例如，球成功传到了一个能够接到的队友手边，才算好合作；
  - 如果传球手把球传到了接球手很难够到的位置，全局 Critic 会给出较低评价，推动策略调整。
- 典型 CTDE：
  - 训练时，Critic 读取全局状态，辅助计算优势函数 advantage，用于更新共享 Actor；
  - 部署时，Critic 完全移除，保证执行只依赖于各自局部观测。


2.4 Trajectory Predictor（轨迹预测器）
--------------------------------------

轨迹预测器是一个辅助模块，用于给 Actor 提供“未来球路”的先验。

输入：
- 历史球轨迹序列（位置 / 速度随时间的序列）。

输出：
- 未来若干帧的球轨迹；
- 或关键落点位置（例如预估 0.5s 后的球在接球手当地坐标系下的位置）。

职责：
- 给 Actor 额外的“预判能力”，帮助其提前做出跑位与起跳决策：
  - 例如预先跑到球将要落下的位置；
  - 在适当时刻起跳以提高接球概率。
- 在当前 `HRLDualHumanoid` 实现中，部分功能已内嵌到 task_obs 中（例如 future_ball_rel_b），未来可以单独拆出为独立模块。


------------------------------------------------------------
3. 训练 vs 部署流程
------------------------------------------------------------

3.1 训练阶段（CT：Centralized Training）
----------------------------------------

参与组件：
- Actor（HLC，参数共享，两机器人各一份实例）；
- LLC（预训练好的低层控制器，执行 Actor 指令）；
- Global Critic（集中式价值网络）；
- AMP / 判别器（维持动作“像人”）。

逻辑流程（高层抽象）：
1. 两个 Agent（A/B）并行在环境中采样：
   - 读取各自观测 obs_A / obs_B（包含局部状态 + 球信息 + 任务特征 + Role 信息）；
   - 通过共享 Actor 输出各自的高层动作 a_high_A / a_high_B；
   - 经由 control_mapping 转成 skill id，再送入 LLC，得到真实关节控制指令；
   - 环境执行一步，更新状态和奖励。
2. 经验存入 Replay Buffer 或 Trajectory（取决于 RL 库）；
3. Global Critic 读取联合状态，评估联合价值 V(s_global) 并辅助构造 advantage：
   - 价值/优势基于双方动作和结果的联合效果，例如：是否完成一次成功的传接球。
4. 使用联合优势 + imitation / AMP 信号更新共享 Actor 参数；
5. 重复迭代，直到协作行为收敛。

注意：
- LLC 权重在 HRL Dual 训练中保持冻结，只使用预训练好的 mixedskills LLC checkpoint；
- Critic 和 AMP 只在训练存在，部署时全部去除。


3.2 执行阶段（DE：Decentralized Execution）
------------------------------------------

参与组件：
- Actor + LLC（不包含 Global Critic 和 AMP）。

逻辑流程：
- 对于机器人 A：
  - 读取局部观测 Obs_A（包括自身、球、对手、预测信息，以及对应 Role_A）；
  - 通过 Actor 输出高层动作 a_high_A；
  - 映射为技能 ID skill_A，经 LLC 得到底层控制，执行动作。
- 对于机器人 B：
  - 同样流程，使用 Obs_B + Role_B。

关键点：
- **A 和 B 之间在执行阶段“互不通信”**：
  - 没有显式的信息通道（例如直接传递意图或状态）；
  - 协作完全通过训练阶段学到的策略 + 面向对方和球的观测来实现。
- 这符合 CTDE 框架：训练时允许看到全局，执行时仅依赖本地信息。


------------------------------------------------------------
4. 代码实现与接口对应关系
------------------------------------------------------------

4.1 任务与环境
--------------

- `skillmimic/env/tasks/hrl_dual_humanoid.py`：
  - 类 `HRLDualHumanoid`：HRL Dual Pass-and-Catch 任务的环境封装。
  - 提供：
    - 高层观测构造（humanoid_obs + obj_obs + other_humanoid_obs + task_obs + condition）；
    - 任务特征 `_compute_task_obs`（例如 ball_to_hand、未来落点 future_ball_rel_b 等）；
    - LLC 基础观测 `get_llc_obs_pair`（供 HRLDualPlayer / HRLDualAgent 使用）；
    - 协作奖励 `_compute_reward`，与 CatchStats 逻辑一致。
  - 定义技能 ID 宏：
    - SKILL_PASS = 4
    - SKILL_CATCH = 3
    - SKILL_RUN = 13
    - SKILL_IDLE = 31
    - SKILL_PICK = 1

- `skillmimic/env/tasks/skillmimic_dual.py`：
  - Dual 环境的基类，包含：
    - CatchStats 统计逻辑（pass / catch 成功率、alive/standing/upright 等）。
    - 对双人 + 球的基础动力学仿真。

4.2 高层 Actor / Player / Agent
-------------------------------

- `skillmimic/learning/hrl_dual_players.py`：
  - 类 `HRLDualPlayer`：
    - 继承 `HRLPlayerDiscrete`，用于 inference / 测试；
    - 负责把 HLC 输出的离散动作映射到 (skill_A, skill_B)，再调用 LLC 生成 312 维（两个 humanoid）底层动作；
    - 使用 `get_llc_obs_pair` 从环境获取 LLC 需要的基础观测。

- `skillmimic/learning/hrl_dual_agent.py`：
  - 类 `HRLDualAgent`：
    - 训练时使用的 HRL Agent，扩展自离散 HRL Agent；
    - 内部逻辑与 `HRLDualPlayer` 类似，但带有训练相关的记录与统计（如 Skill Monitor）。

- `skillmimic/learning/hrl_players_discrete.py` / `hrl_agent_discrete.py`：
  - 单人 HRL 的高层 Player/Agent；
  - 负责解释 `config['control_mapping']`，把 HLC 离散动作映射为 LLC skill id。

4.3 低层 LLC 与技能编码
------------------------

- LLC 的基础训练配置：`skillmimic/data/cfg/train/rlg/skillmimic_as_llc.yaml`；
- LLC checkpoint：`skillmimic/data/models/mixedskills/nn/skillmimic_llc.pth`；
- 技能 ID 来源：
  - `skillmimic/utils/motion_data_handler.py` 中，motion 文件名前三位数字（例如 "004pass_xxx.pt" -> 4）。
- Skill IDs 在各 HRL 任务配置中的使用（control_mapping）：
  - Dual Pass-and-Catch：
    - `skillmimic/data/cfg/train/rlg/hrl_dual_humanoid.yaml`：
      - control_mapping: [4, 13, 31, 3, 13, 31]
  - Circling / Heading / Throwing / Scoring 等任务：
    - `hrl_humanoid_discrete_circling.yaml`、`hrl_humanoid_discrete_heading.yaml`、`hrl_humanoid_discrete_throwing.yaml`、`hrl_humanoid_discrete_layupscore.yaml`。


------------------------------------------------------------
5. 对后续 Agent 实现者的注意事项
------------------------------------------------------------

1. 遵守 CTDE：训练阶段可以访问全局信息（尤其是 Critic），部署阶段必须只依赖各自观测。
2. Skill 映射要统一：
   - 所有使用 LLC 的 HRL 任务都必须通过 control_mapping 把离散动作映射到一致的 skill id 语义。
3. 观测设计要包含“对方 + 球 + 预测信息”：
   - 双人协作完全依赖每个 Agent 的观测来推断队友行为，必须保证任务观测中有足够的信息。
4. 奖励设计要兼顾“成功率 + 稳定性”：
   - 例如：catch_success、catch_fail、pass_direction、ball_to_hand、standing、upright、ground_contact_penalty 等；
   - 与 CatchStats 中的统计指标保持一致，方便评估。
5. 轨迹预测模块可以作为单独子网络：
   - 但要避免给 Actor 过于“作弊”的信息（例如直接给出最佳动作），更适合提供未来球位置/速度等物理可推导量。
